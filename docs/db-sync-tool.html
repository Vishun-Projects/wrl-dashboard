Tips & Best Practices
Read these before you start. They'll save you hours of debugging and prevent hammering the source DB.
Source DB Load
⚠
Never use OFFSET for large tables
OFFSET 100000 forces the source DB to scan and discard 100k rows every time. At 5 lakh rows, this becomes brutally slow and CPU-intensive. Use cursor-based pagination (WHERE id > last_id) instead — it's O(log n) with an index, not O(n).
✓
Add delay between page fetches
Even 100–200ms delay per page drastically reduces DB connection pressure. With 5 concurrent workers each fetching 500 rows/page, you're already making ~5 queries/second. Delay keeps it sane. Set it in Config → Delay Between Pages.
⚠
Keep concurrency low (3–8 workers)
Running 20 parallel workers against a source DB that's also serving live traffic is a recipe for timeouts and angry ops teams. Start at 3–5 workers, monitor the source, then increase. The 120s timeout suggests the server is already under some pressure.
ℹ
Schedule full sync during off-peak hours
If the source DB is a production system, run the full export at night — 2 AM to 6 AM. Incremental syncs during the day are fine since they're small queries. Use your OS cron or trigger this tool manually at off-peak time.
✓
Request timeout = 110s, not 120s
Give yourself a 10s buffer before the server's hard 120s kill. If your fetch is still running at 110s, abort it, save the cursor, and retry that page. This prevents silent failures where the server kills the connection mid-response.
Pagination Strategy
✓
Cursor pagination: the right way
Store the last row's id (or composite key) after each page. Next request: ?after_id=50000&limit=500. The source runs WHERE id > 50000 ORDER BY id ASC LIMIT 500 — lightning fast with an index regardless of table size. This tool saves the cursor after every page so crashes are harmless.
ℹ
Page size sweet spot: 500–1000 rows
Too small (50 rows/page) = too many round trips, each with network overhead. Too large (5000 rows/page) = risk hitting 120s timeout if rows are heavy. 500 is safe for most schemas. Increase to 1000 only if rows are narrow (few columns, no blobs).
⚠
Watch for tables with BLOBs / large text
If a table has TEXT, JSON, or BLOB columns with large content, 500 rows might still be huge. If you're hitting timeouts on specific tables, reduce that table's page size manually — use the Job Queue page to override per-table settings.
Supabase Destination
✓
Use service_role key, not anon key
The anon key is RLS-restricted. For bulk upserts during sync, use the service_role key found in Supabase → Project Settings → API. Never expose this key in a public frontend — this tool runs locally in your browser only.
ℹ
Pre-create tables in Supabase before syncing
This tool upserts data but does NOT auto-create tables. You need the destination schema set up first. Generate CREATE TABLE statements from the source schema and run them in Supabase SQL editor before hitting Start.
✓
Disable RLS during initial full import
RLS policy checks on every row slow down bulk inserts. During the first full sync, consider disabling RLS on destination tables temporarily: ALTER TABLE your_table DISABLE ROW LEVEL SECURITY; — re-enable after sync is done.
⚠
Upsert requires a unique constraint
Supabase upsert (onConflict) requires the conflict column to have a unique index or primary key. If your source table's primary key maps to id in Supabase, make sure it's PRIMARY KEY or UNIQUE — otherwise every row gets duplicated on retry.
Incremental Sync
ℹ
Hard deletes are invisible to incremental
If source records are hard-deleted, your incremental sync won't know — it only fetches rows WHERE updated_at > last_sync. For deletions, you need the source to use soft deletes (is_deleted = true) or you need a separate deleted-records log/audit table to sync from.
✕
Don't trust client-side timestamps for incremental
Always use the source server's updated_at — never compute it client-side or derive it from your last fetch time. Clock skew between client and server can cause you to miss rows that were updated in between. Let the source DB own the timestamp.
Crash Recovery
✓
Cursor saves happen per page, not per table
This tool writes last_cursor to localStorage after every single page fetch. If your browser crashes at row 49,500 of a 5-lakh table, you resume from row 49,500 — not from the beginning. Check the Job Queue page to see exact cursor positions.
ℹ
Keep this tab open during full sync
This is a browser-based tool. If you close the tab, the sync stops. State is saved in localStorage, so you can re-open and resume — but active workers will stop immediately on tab close. For production, move this logic to a server-side Node.js script using the same pattern.
⚠
Test on 2–3 small tables first
Before you fire off all 1812 tables, test with 2–3 small ones. Verify cursor pagination works, upsert is writing correctly, and there are no auth errors. Fix config issues on small tables before running the full job — saves hours of waiting only to fail at the end.
